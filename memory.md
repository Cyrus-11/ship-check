## Objective and current state

Build Shipcheck v0.1, a NestJS standalone release-readiness CLI for Node.js/TypeScript repositories using npm. Follow [AGENTS.md](AGENTS.md), including ordered context reading on a new session. **Features 01–11 are implemented and verified. Next: Feature 12 Scan Orchestration.** All four scanners and their registry exist, but the full scan pipeline is still unfinished. No unresolved decision or blocker is recorded.

Scope stays help, version, scan, and scan --ci, with four sequential scanners: Git, Build, Tests, Environment. No HTTP server, database, frontend, configuration system, extra scanners, other package managers, or public npm publication. Shipcheck-owned operations are read-only; repository-owned build/test scripts can have side effects. Never expose environment values, raw subprocess output, or error stacks in reports.

Detailed evidence lives in [progress-tracker.md](context/progress-tracker.md), plans in [build-plan.md](context/build-plan.md), and library decisions in [library-docs.md](context/library-docs.md).

## Implemented behavior and boundaries

- Bootstrap runs once through CommandFactory; main preserves the shebang and reflect-metadata import. CommandsModule registers root/scan commands and imports ScanModule. Help/version work independently of target cwd; version comes from Shipcheck's own manifest.
- **ScanService now performs project discovery, then returns the shell result.** scan() awaits discover(), which resolves process.cwd() once, reads only <cwd>/package.json via FileSystem (no parent traversal), narrows untrusted JSON into the PackageJson projection, applies directory-basename fallback for a missing/blank name, and builds the immutable ScanContext. For a valid target it still returns a failed gate as Pick<ScanReport, "gatePassed"> and prints no report. Local/CI shell exits remain 0/1; usage/unexpected failures exit 2. Ambient CI does not select CLI mode.
- **Feature 06 discovery failures exit 2 with safe stderr text.** ProjectDiscoveryError (src/scan/project-discovery.error.ts) carries fixed messages plus an internal cause. bootstrap recognizes it and writes: missing → "Shipcheck could not scan this directory: package.json was not found.", invalid → "...package.json is not valid JSON.", unreadable → its own message, each followed by "Run the command from the root of a Node.js project.". Generic errors still yield the generic fatal message. Both new canonical messages are documented in [cli-output-rules.md](context/cli-output-rules.md). ScanModule imports InfrastructureModule so ScanService injects FileSystem.
- Feature 04 added domain types and Scanner under src/common/, frozen SCAN_ORDER (git, build, test, env), weights of 25 each, and READY/REVIEW thresholds of 90/70. It reused exit constants and removed ScanShellReport plus obsolete generated artifacts.
- Feature 05 added process request/result contracts and InfrastructureModule with ProcessRunner, FileSystem, Clock, operational errors, and execution limits. ScannersModule imports these providers; ScanModule uses FileSystem for project discovery.
- ProcessRunner uses separate executable/arguments, shell:false, closed stdin, captured output, explicit absolute cwd/timeouts, and an inherited environment snapshot plus overrides. It never mutates request or parent environment. Windows keys are normalized; undefined removes a key. TestScanner supplies CI: "true".
- Ordinary numeric exits are unchanged. Timeout returns timedOut:true with synthetic exitCode 1. Missing executable/cwd and start failures throw ProcessStartError; invalid requests, output limits, signals/cancellation, and other operational failures throw ProcessExecutionError. Public messages are fixed; causes/output stay internal.
- Execa text buffers count characters: capture uses encoding:buffer with 1,000,000 bytes per stream, then UTF-8 decoding. Check failure flags before numeric exits: buffer failure can have exitCode 0. Timeout inputs are integers from 1 through 2,147,483,647 ms. Central limits provide Git 10 seconds, build/test 120 seconds, and termination grace 5 seconds.
- The user approved Execa's internal cmd.exe launcher for resolved npm.cmd while retaining shell:false and prohibiting Shipcheck-built shell strings. Architecture/standards record this exception. Windows supports native .exe/.com and npm.cmd; arbitrary shebang/batch launchers and metadata-denied App Execution Aliases fail safely.
- FileSystem owns runtime node:fs/promises reads: UTF-8 readText, exists (false only for ENOENT), and Windows executable lookup. Lookup checks PATH/PATHEXT, quoted directories, extension/case rules, and current-directory control before Execa so missing commands cannot appear as ordinary exit 1. Clock uses monotonic performance.now().
- **Feature 07 added the Git scanner.** src/scanners/git/git.scanner.ts implements the Scanner contract (id "git", name "Git", weight from SCANNER_WEIGHTS.git). It receives ScanContext (never reads process.cwd()) and runs read-only git rev-parse --is-inside-work-tree, git branch --show-current, and git status --porcelain via ProcessRunner under the 10s Git timeout, returning exactly one fully populated ScanResult. src/scanners/scanners.module.ts imports InfrastructureModule and provides/exports GitScanner.
- Git scanner mapping: work-tree check non-zero → failed ("Not a Git repository"); post-work-tree non-zero exits, spawn failures, and timeouts → error; clean tree → passed, dirty tree → failed. Passing summary reports the branch name, or "detached HEAD" when git branch --show-current is empty; dirty summary reports the changed-file count only. details is always [] — no changed file paths are leaked in summary or details.
- **Feature 08 added the Build scanner (pushed at 47a4a48).** src/scanners/build/build.scanner.ts implements the Scanner contract (id "build", name "Build", weight from SCANNER_WEIGHTS.build). It receives ScanContext (never reads process.cwd()) and reads packageJson.scripts.build; a missing or blank script maps to failed ("package.json has no build script") without spawning npm. Otherwise it runs repository-owned npm run build via ProcessRunner under the 120s build timeout. ScannersModule provides/exports BuildScanner.
- Build scanner mapping: zero exit → passed ("npm run build passed"); non-zero exit → failed ("npm run build failed"); timeout → failed ("npm run build timed out after 120s", the 120 derived from PROCESS_LIMITS.BUILD_TIMEOUT_MS/1000); output-capture overflow (ProcessExecutionError reason "output_limit") → failed ("npm run build failed") per cli-output-rules §171 (a repo-owned build failure must not be labeled a Shipcheck error); ProcessStartError and other ProcessExecutionError reasons → error ("Scanner could not complete"). details is always [] and no build stdout/stderr is rendered. Deliberate divergence from GitScanner: a build timeout is failed, not error (inline comment marks the branch to prevent a future "consistency" regression).
- **Feature 09 added the Test scanner (committed at 900497b).** src/scanners/test/test.scanner.ts implements the Scanner contract (id "test", name "Tests", weight from SCANNER_WEIGHTS.test), mirroring BuildScanner. It receives ScanContext (never reads process.cwd()) and reads packageJson.scripts.test; a missing or blank script maps to failed ("package.json has no test script") without spawning npm. Otherwise it runs repository-owned npm test via ProcessRunner under the 120s test timeout with a CI=true env override (parent process.env never mutated). ScannersModule provides/exports TestScanner.
- Test scanner mapping: zero exit → passed ("npm test passed"); non-zero exit → failed ("npm test failed"); timeout → failed ("npm test timed out after 120s", the 120 derived from PROCESS_LIMITS.TEST_TIMEOUT_MS/1000); output-capture overflow (ProcessExecutionError reason "output_limit") → failed ("npm test failed") per cli-output-rules §171 and decision D5 (Build/Test symmetry); ProcessStartError and other ProcessExecutionError reasons → error ("Scanner could not complete"). details is always [] and no test stdout/stderr is rendered. As with BuildScanner, a test timeout is failed, not error.
- **Feature 10 added the Environment scanner.** src/scanners/env/env.scanner.ts implements id "env", name "Environment", weight SCANNER_WEIGHTS.env, injecting FileSystem and Clock. It parses .env.example for required keys with pinned dotenv 18.0.4, then accepts a trimmed non-empty value from any of .env, .env.local, or an own process.env property. Sources are evaluated independently; empty values cannot mask another source. Example placeholders never satisfy presence. Parsed values are reduced to names locally and never enter results or process.env.
- Environment outcomes: absent/disappearing example -> skipped ("No .env.example found"); empty/comment-only contract -> passed ("0 required variables are present") without optional reads; complete presence -> passed with canonical singular/plural count; missing names -> failed with the canonical count and all missing names sorted alphabetically. Optional ENOENT, including a read race, is ignored; other filesystem/parser failures -> error ("Scanner could not complete") without leaking error contents. Within one file duplicate keys follow dotenv's final declaration; required names count once. Only the reporter limits displayed details. ScannersModule provides/exports EnvScanner alongside the other three concrete scanners.
- **Feature 11 added the ordered scanner registry (committed and pushed at 24c0b6a).** `src/scanners/scanner.tokens.ts` defines the shared `SCANNERS = Symbol("SCANNERS")`. A private `FactoryProvider<Scanner[]>` in `src/scanners/scanners.module.ts` explicitly injects GitScanner, BuildScanner, TestScanner, EnvScanner and returns those existing singleton instances in that order. It exports the token alongside the concrete providers. `src/scan/scan.module.ts` imports ScannersModule alongside InfrastructureModule and still exports only ScanService.
- The factory performs no checks or target-file/process operations. The array retains the documented Scanner[] shape; there is no sorting, runtime discovery, registration API, or new dependency. ScanService constructor injection and execution remain Feature 12; no unused registry dependency was added early. The [scanner registry](context/scanner-registry.md) now marks both concrete scanners and the ordered provider complete.
- Orchestration, scoring, reporting, full-pipeline fixtures, and installed-package smoke tests remain unfinished. ScanService still performs discovery and returns the temporary failed gate without running scanners or printing a report.

## Durable decisions and lessons

- MIT license; package remains private. Baseline: Node >=22.12, native ESM, strict TypeScript NodeNext, runtime .js relative imports. Verified environment: Windows, Node 24.16.0, npm 11.13.0.
- Pinned Nest common/core/testing 11.2.5, nest-commander 3.21.0, TypeScript 5.9.3, Vitest 5.0.1, Execa 10.0.1, dotenv 18.0.4, reflect-metadata 0.2.2, RxJS 7.8.2, @types/node 22.20.4. Do not blindly upgrade Nest: the discovery dependency required Nest 11 despite nest-commander advertising Nest 12 compatibility. The current tree passed strict peer installation. Use a Node version supported by Vitest for development; Node 24 was verified.
- npm test builds production and compiles tests with tsc, then Vitest runs .test-dist/test/**/*.spec.js. This preserves real Nest constructor metadata. Test helpers may access files/processes directly; runtime consumers use adapters. Production has no test switches or test files.
- nest-commander child commands do not inherit root strictness/exit overrides. ScanCommand.setCommand explicitly disables excess arguments and uses the shared throwing parser override. Returning from an override permits Commander to exit before cleanup. Bootstrap recognizes only ParserExitSignal, applies exits after cleanup, and lets cleanup failures override success.
- Native subprocess tests are necessary for the package-version JSON loader: Vitest's in-process data-URL imports dropped JSON attributes. Do not weaken the runtime loader to accommodate that transform.
- PackageJson is a validated readonly subset, not arbitrary JSON. Feature 06 discovery narrows unknown input and selects string name and scripts.build/scripts.test only, omitting non-string/unsupported fields, and applies the documented directory-basename fallback for a missing/blank name. Context/package readonly is compile-time protection, not runtime deep freezing (no Object.freeze per architecture line 236). Report consistency belongs to later providers.
- Feature 06 lesson: exactOptionalPropertyTypes rejected a builder type that unioned undefined into the optional scripts projection. Type the builder and projectScripts return as { build?: string; test?: string } (and | undefined only on the function return, not the object field) so it assigns to PackageJson. Do not add undefined to the target's optional property types.
- The exit selector permanently needs only the report gate field. Do not weaken complete ScanReport fields or invent results/metadata to satisfy the temporary shell.
- Execa's full generic result conflicted with exactOptionalPropertyTypes. A private Pick of consumed fields resolved this without production assertions or Execa types in public contracts.
- Windows taskkill was denied inside the tool sandbox. Execa killed only the direct process, leaving descendants/pipes alive. Confirmed permission failure, identified and terminated only fixture-owned ancestry with normal permissions, and removed the leftover fixture. Process-tree checks passed outside the sandbox. Cleanup is best-effort, not containment or a hard deadline.
- The tree fixture records script/child PIDs and has independent emergency cleanup. Under the full parallel suite, the original two-second npm timeout expired before script startup. Recovery traced the missing PID marker; matching the ten-second npm smoke allowance fixed the test timing issue.
- Patch/shell helpers sometimes stall or fail Windows sandbox setup. Inspect partial edits before retrying, stop stalled sessions, and prefer short commands with login:false. Long PowerShell handoff writes stalled again during this save; the session was stopped and the patch tool used instead. Do not blindly replay edits or weaken Git ownership checks; the workspace-specific safe.directory entry already exists.
- Feature 07 lesson: strict index access (noUncheckedIndexedAccess) flagged reading a mock call tuple in the unit spec (TS2532). Use optional chaining on the mock call array (e.g. run.mock.calls[0]?.[0]) rather than a non-null assertion.
- Feature 07 lesson: git integration fixtures must isolate from the developer's global/system Git config, hooks, and signing. Set GIT_CONFIG_GLOBAL/GIT_CONFIG_SYSTEM to non-existent paths (plus GIT_CONFIG_NOSYSTEM and GIT_TERMINAL_PROMPT=0), pin the branch with init.defaultBranch=main, and pass commit identity and commit.gpgsign=false inline. Only the setup commands need this; the scanner's read-only commands inherit the real environment.
- Feature 07 lesson: under the full parallel Vitest suite (14 workers), the pre-existing npm-subprocess infrastructure integration test can time out; it passes in isolation. This is a known test-infrastructure susceptibility, not a Git-scanner regression — do not "fix" it by weakening the Git scanner or its tests.
- Feature 08 review dispositions (/review on 2026-09-24): (#1) output-capture overflow now maps to failed rather than error per cli-output-rules §171; gate impact unchanged (both 0/25 applicable points). GitScanner left unchanged — git is a Shipcheck-owned command, so §171's "build or test" clause does not apply. (#2) Unexpected non-process throws still propagate from run(), matching GitScanner; cross-scanner isolation deferred to Feature 12 orchestration. (#3) No live 120s timeout integration test — mapping is unit-tested and the adapter's real timeout was covered in Feature 05. (#4) The integration test intentionally omits a "repository unchanged" assertion because repo-owned build scripts may have side effects per AGENTS.md.
- Feature 09 lessons: (D5 confirmed) test output-capture overflow and timeout map to failed, not error, per cli-output-rules §171 — Build/Test symmetry; CI=true is injected only into the test subprocess via the ProcessRunner env override, and both unit and integration tests assert the parent process.env.CI is unchanged. The scaffold guard in test/unit/scaffold.spec.ts ("keeps tests out of production output") previously flagged any "test" path segment in dist/ and falsely matched the legitimate production dir dist/scanners/test/; anchoring the directory match to the dist root (^test) keeps the leaked-test-tree guard while allowing the mandated scanners/<id> layout. Do not broaden it back.
- Feature 10 review found inherited process.env properties such as toString could otherwise cause an error instead of a missing-name failure. Object.hasOwn prevents this; two regression cases cover absent and file-supplied values. Do not remove the own-property check.
- dotenv's installed exports are dist/index.cjs with dist/index.d.ts. Native named ESM import works; parse accepts string/Buffer and returns a string map. Its README debug-option example differs from installed types (fast only); Shipcheck passes no options. Parsing is permissive; no strict syntax validation or variable expansion is added. Node >=12 fits the existing baseline.
- Feature 10 and Feature 11 full suites used NO_COLOR=1 and npm test -- --maxWorkers=4 with normal Windows process permissions. Four workers reduce existing npm fixture startup contention; this changes scheduling only, not test behavior. Do not rerun known failing process-tree cleanup inside the restricted sandbox.
- Feature 11 DI tests use a consumer with @Inject(SCANNERS) in a module importing ScannersModule to prove token export visibility. Unrestricted moduleRef.get alone does not prove that boundary. The native registry probe imports the symbol and classes from the same production dist tree; source/test-output symbols have different identities.
- Feature 11 inspected installed Nest common/core/testing 11.2.5 declarations/source and official general custom-provider/module documentation. Version-specific v11 web pages could not be fetched; compilation, DI tests, and native production resolution verified the installed APIs. No dependency/engine change was needed.
- npm registry access failed with sandbox EACCES and succeeded with network permission. PowerShell stripped quotes from a node -e probe; piping a literal here-string to node --input-type=module fixed it. Prefer literal stdin or checked-in test helpers for multiline Node probes.
